# Local Setup — Gestion École

Everything needed to develop Gestion École on your machine, against a **local** database.
Nothing here touches a school's real (hosted) project.

---

## 1. Prerequisites

| Requirement | Version | For |
| --- | --- | --- |
| Node.js | ≥ 22.12 | everything (`@supabase/supabase-js` and Vite 8 require it) |
| npm | ≥ 10 | dependencies (`npm ci` uses `package-lock.json`) |
| Docker Desktop | current | the local Supabase stack |
| Supabase CLI | current | creating / starting / resetting the local stack |
| Rust (MSVC toolchain), Visual Studio C++ build tools, WebView2 | stable | **desktop builds only** |

`bun.lock` is kept in sync with `package-lock.json` for hosts that install with Bun (the
`bunfig.toml` 24-hour release-age guard applies there). Change dependencies through npm and
regenerate both.

---

## 2. Local database

```bash
supabase start
```

creates the stack from `supabase/config.toml` and applies every migration in
`supabase/migrations/`. Ports (moved off the CLI defaults so the stack can coexist with
another project's stack on 5432x):

| Service | Port |
| --- | --- |
| API (Kong) | **55321** |
| Postgres | 55322 |
| Studio | 55323 |
| Inbucket (local mail: password resets, invitations) | 55324 |

Only one stack can hold these ports at a time. If another project's stack already uses them,
stop it first or change the ports in `supabase/config.toml`.

`supabase start` prints the local keys; `supabase status` prints them again. The database
container is `supabase_db_<project_id>` (see `docker ps`); the SQL test scripts take it from
`$DB_CONTAINER`.

Rebuild the local schema from scratch: `supabase db reset` (local only — never with
`--linked`).

## 3. Environment files

| File | Committed? | Used by |
| --- | --- | --- |
| `.env.example` | yes | the list of variables, with placeholders |
| `.env.local` | **no** | `npm run dev`, the e2e suites, local desktop builds |
| `.env` | **no** | release desktop builds (a school's hosted project) |

Vite loads `.env.local` over `.env` in every mode, so with a `.env.local` present the dev
server **and** a local `npm run build` use the local stack.

`.env.local` for the local stack:

```env
VITE_SUPABASE_URL="http://127.0.0.1:55321"
VITE_SUPABASE_PUBLISHABLE_KEY="<publishable / anon key from supabase status>"
SUPABASE_URL="http://127.0.0.1:55321"
SUPABASE_PUBLISHABLE_KEY="<same>"
SUPABASE_SERVICE_ROLE_KEY="<secret / service_role key from supabase status>"
```

The local stack's keys are local-only, but keep the file uncommitted anyway (it is in
`.gitignore`). Never put a hosted project's service-role key in any file of this repository.

## 4. Run

```bash
npm ci
npm run dev        # http://localhost:8080
```

Sign-up always creates students. Create a local administrator the way DEPLOYMENT.md §5
describes (Studio at http://127.0.0.1:55323 has the same SQL editor), or use the demo data
below.

`src/routeTree.gen.ts` is generated by the dev server: start it once after adding a route,
then run `npx tsc --noEmit`.

## 5. Optional demo data (local only)

```bash
npm run seed:demo          # idempotent
npm run seed:demo:fresh    # also clears other local groups and leftover test accounts
npm run verify:demo        # signs in as each demo role and checks what it sees
```

Demo accounts end in `@demo.gestion-ecole.local` (admin, teacher, student; details in
[docs/local-demo-data.md](docs/local-demo-data.md)). The seed refuses any Supabase URL that is
not `127.0.0.1` / `localhost`. To remove all demo data:

```bash
docker exec -i "$DB_CONTAINER" psql -U postgres -v ON_ERROR_STOP=1 < scripts/reset-demo-data.sql
```

## 6. Tests

```bash
npx tsc --noEmit
npm run test:unit
```

**E2E suites** (`scripts/e2e/`) run against the local stack and the dev server, create
throwaway accounts through `scripts/e2e/fixtures.mjs` and remove them. `fixtures.mjs` reads
`.env.local` and refuses any non-loopback API.

Before running a suite, check it does not hard-code another stack: these still contain
`54321` or `5173` and must not be run until they read `fixtures.mjs` (QA-01):
`verify-enrollment-integrity`, `verify-enrollment-ui`, `verify-level-statistics`,
`verify-role-integrity`, `verify-rtl`, `verify-teacher-lifecycle`, `verify-teacher-workspace`,
`verify-teachers-ui`.

SQL suites (`scripts/e2e/verify-*.sql`) run inside one transaction that is always rolled back:

```bash
docker exec -i "$DB_CONTAINER" psql -U postgres -v ON_ERROR_STOP=1 -q < scripts/e2e/verify-fees.sql
```

## 7. Desktop app

```bash
npm run desktop:ui:local                    # UI against the local stack -> dist-desktop/
node scripts/e2e/verify-desktop-offline.mjs # offline restart / queue / sync test (local)
npm run desktop:build                       # installers, from the values in .env
```

`desktop:ui:local` reads `.env.local` and sends server-function calls to
`http://localhost:8080` (keep `npm run dev` running). A release build reads `.env`, which
must also set `DESKTOP_SERVER_ORIGIN` (DEPLOYMENT.md §9). Every build generates the window's
Content Security Policy for its own backend (`src-tauri/tauri.build.conf.json`, not committed)
and refuses to finish if the bundle contains secret material.

## 8. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| Port 8080 in use | `netstat -ano \| findstr :8080`, then stop that process |
| "Missing Supabase environment variables" | `.env.local` missing or incomplete; restart the dev server after editing it |
| Changes to `.env.local` not applied | Vite reads env files at startup: restart `npm run dev` |
| Password-reset mail never arrives locally | it is in Inbucket, http://127.0.0.1:55324 |
| `npm run format` rewrites hundreds of files | known (TD-14): run it as its own commit, or not at all |
